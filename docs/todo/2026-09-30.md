- [x] BUG: chrome has 10MB min download capture limit configured but it is capturing smaller file. fix, add test cases to harden it. This bug was there before seems to have resurfaced.
      **Fixed.** Both symptoms turned out to be one bug: every layer's minimum check is
      guarded by `size > 0`, so a URL whose size is unknown walked straight past the
      configured threshold. Chrome reports `totalBytes: 0` for any response without a
      Content-Length, and the server's fallback probe has a 1.8 s budget that a slow or
      auth-gated origin can blow.

      The threshold is now handed to `HTTPEngine`, which probes every download before
      transferring a byte, and refuses there against the authoritative size
      (`HTTPEngine._enforce_browser_min_size`). The capture path still short-circuits when
      it *can* size the file, so the common case still costs one comparison. Hand-added
      downloads are deliberately never gated - the setting means "minimum size to
      *intercept*", and a user pasting a 4 KB URL should still get it.

      Covered by `tests/test_browser_capture_gating.py` (28 tests).

- [x] BUG: verify that the download was from a github private repo, why did it not start download, are we capturing that download correctly?
      **Answer: no, we were not capturing it correctly.** Verified read-only against the
      log and the database: both rows are `blob:https://github.com/4719d4f4-...` with
      `total_size = 0`, captured through the browser path on a github.com page - consistent
      with a private repo. A `blob:` URL is a browser-internal object reference with no HTTP
      transport, so it can never be fetched by an external downloader.

      The log shows the cost: `HEAD request failed for blob:...` followed by five retries
      at 5s / 10s / 20s / 40s / 60s before `error` - about two and a half minutes per
      file, twice over.

      **Root cause: an asymmetry between the two interception engines.** The Firefox engine
      rejected `blob:` and `data:` (`background.js:328`); the Chromium engine had no scheme
      guard at all and only skipped loopback. The same page was therefore captured on
      Chrome and correctly skipped on Firefox - which is why this looked like a
      Chrome-specific regression when resurfacing.

      **Fixed at all three layers**, because an unpacked extension does not auto-update,
      so a server-side check is not redundant:
      - extension: one shared `isCapturableUrl()` now used by *both* engines; a test asserts
        both call it so they cannot drift apart again;
      - server: `POST /add` refuses any scheme other than `http` / `https` / `magnet` with
        `reason: unsupported_url_scheme`, before a row is queued and before a probe is
        spent;
      - engine: unchanged, since such a URL can no longer reach it.
